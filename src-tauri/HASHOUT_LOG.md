# HASHOUT_LOG · desktop shell and window

Reasoning behind the shell's startup, newest first.

## 2.19.0 · the engine ends with the app on Windows, and a failed start says what the engine said

- **Which way.** FormVis's: the engine is still started through tauri-plugin-shell's sidecar, so `win_job.rs` takes it into the job by its process id (`hold_pid(child.pid())`, `OpenProcess` with `PROCESS_SET_QUOTA | PROCESS_TERMINATE`, then `AssignProcessToJobObject`). The job is made with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, so Windows ends the engine when the shell's last handle to the job goes, however the shell ends. `kill_backend` ends the job before it kills the child. `windows-sys` 0.61.2 is a Windows-only dependency; it was already in `Cargo.lock` through tauri, so the lock gains one line in formcut's own entry and no new package.
- **The failure text.** `engine_start.rs` holds the sentences, the engine's last twelve lines (control characters dropped, 300 characters a line, never a line with the window key), and the path of the newest `engine-*.log` under the data folder's `logs` (found the way `backend/app/paths.py` finds the data folder: `FORMCUT_DATA_DIR`, a `portable` folder beside the program, then the system's place). The exit code is said in words. Exit code 2, which the engine returns when another copy holds the data folder, has a sentence of its own in place of "The local engine stopped (exit Some(2))". An engine that stops while the window is open says so in its own sentence.
- **The order.** The dialog is shown first, then the splash is closed, the engine ended and the app left, as in the entry below. A start that fails before the engine runs (missing sidecar, spawn error) no longer panics in `setup`: the dialog is shown from a thread of its own so `setup` returns.
- **The wait.** 90 seconds for the address (the owner's choice for the family), 10 for the key after it, and one second after the engine stops so its last lines can still arrive.
- **Checked.** The two files in a scratch crate: `cargo check` and `cargo clippy` for `x86_64-pc-windows-msvc` clean, six tests of the plain functions pass, `cargo fmt --check` clean, `cargo metadata --locked` agrees. The shell itself was not compiled (no WebKit here).

## Unreleased · the engine is told who started it, and a failed start is said before the splash closes

- **The process id.** The engine is spawned with `FORMCUT_SHELL_PID` set to the shell's own process id (main.rs, one `.env` line beside its two twins). From this version a packaged engine that does not get it takes itself for one started alone, opens the app and serves nothing (`backend/desktop_entry.py`), so the app must set it; with it the engine also leaves within about two seconds of the shell ending, however the shell ended, and records the shell in `engine.owner` so the next start can tell a leftover engine from a live one. The 2.17.0 shell set no such variable, so there was none to keep.
- **The order.** After the loop in `supervise` (engine_lifecycle.rs) the splash was closed and then the failure was said. When no editor window exists yet the splash is the last window, and closing the last window can end the app before the dialog is seen, which is the silent exit a tester met in another app of the family. The dialog is now shown first and the splash is closed when it returns. Two statements in another order; when the editor window exists the splash is already gone and the second statement does nothing, as before.
- **Not compiled, not run.** No WebKit here, so the shell was not built on any system; `cargo fmt --check` is clean. Whether the dialog is in front of the splash on each system has not been seen.
- **Held.** The rest of the family's shell side: the Windows job object (`win_job.rs` needs a `std::process::Child`, and this shell starts its engine through tauri-plugin-shell), `engine_start.rs` with the failure text that carries the engine's last lines and the log's path, and a sentence of its own for exit code 2 (a second start now reads "The local engine stopped (exit Some(2))").

## 2.16.0 · the shell hands the window its key

- **The change.** The engine is spawned with `FORMCUT_WINDOW_KEY_STDOUT=1` (main.rs). `supervise` (engine_lifecycle.rs) keeps a second buffer for stdout only and takes the key from a whole line `formcut-window-key: <32 or more of A-Z a-z 0-9 _ ->` there. The address is read as before (stdout or stderr, then the health check); once it is healthy the port and the moment are kept. The window is built only when both the address and the key are known, with one `initialization_script` that sets `window.__FORMCUT_WINDOW_KEY` when `location.origin` is the engine's own `http://127.0.0.1:<port>` (tauri 2.11.5's `WebviewWindowBuilder::initialization_script(impl Into<String>)`).
- **How long it waits.** Before the address: the 40 s that main already had, unchanged. After the address: 10 s for the key, counted from the moment the address was found healthy; when they run out the loop ends and takes the existing failure path ("did not hand the window its key") with no window. An engine that exits, errors or closes its output takes the existing path at once. The failure path is the code after the loop, so it runs once.
- **Order seen.** Engine from source with the variable set: the key line first, on stdout, once; the address on stderr after uvicorn starts. Both orders are handled.
- **Checked.** Not compiled (no WebKit here); `rustfmt --check` clean. The loop was copied into a scratch crate (tokio 1.53.1 and regex 1.13.1 as pinned) with a channel for the events and run: key then address, window at 0.0 s; address then key 3 s later, window at 3.0 s; both in one chunk, window at 0.0 s; address then 11 s of silence with the output open, failure at 10.0 s and no window; 35 s of silence then key and address, window at 35.0 s; exit before the address, failure at 0.0 s; address then exit 2 s later, failure at 2.0 s; address then the output closed, failure at 1.0 s; 45 s of silence, failure at 40.0 s. A first copy set the key message when the address arrived, which then also showed when a running engine went away later; the message is now set only when the 10 s run out.

## 2.13.2 · splash parity with formvis

- **Why the main window is built hidden.** It is created only once the engine answers, so before that the person sees nothing; with the splash up first the launch shows a card at once. On macOS a hidden window's web view stops its animation frames and the page renders through them, so the window is built hidden and `conceal` puts it on screen at alpha 0 with clicks passed through; elsewhere it is built hidden and shown by `show_main`. Both carry the page's #0a0a0a background, so no white frame shows.
- **Timing.** `show_main` waits until 2600 ms since `mark_launch`, runs `formcutSplashDone` so the bar completes over 220 ms, shows the main window whole and closes the splash. A 20 s fallback shows the window if the page never reports, so a page that failed to load cannot leave only the splash.
- **Corners.** The splash window is transparent and its page draws the 16 px card. macOS still painted a square behind it, so `round_splash` makes the window non-opaque with a clear background and masks the content layer to the same radius, then shows it. Elsewhere it just shows.
- **Remote origin.** The main window shows the page the engine serves on 127.0.0.1, a remote origin to Tauri, so the capability gains a remote URL list and `app_ready` gets a generated allow permission through `build.rs`. The page calls it through `__TAURI_INTERNALS__`, since the frontend has no Tauri API dependency, two frames after its first content is mounted.
- **Failure paths.** If the engine never starts or the window cannot be built, the splash is closed before the error dialog so the dialog is not hidden behind it.
- **Differs from formvis.** No traffic-light placement, window-state memory or single-instance handling: formcut has none of them.
