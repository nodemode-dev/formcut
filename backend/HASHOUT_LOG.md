# HASHOUT_LOG · engine

Reasoning behind engine changes, newest first.

## Unreleased · comments in the build scripts name the release without history

- **What was wrong.** Earlier on this branch `setup/build_release` and `setup/build_portable_linux` gained comment text saying that formcut-binaries is the older name of formai-binaries. The two comments are back to the shape they had on main with only the new name in them.
- **Where it is said instead.** Builds made before the rename use `formcut-binaries`, which keeps working; the docstrings of `ffmpeg_fetch.py` and `setup/bundle_ffmpeg.py`, `.docs/wiki/Packaging.md` and `src-tauri/ffmpeg/README.md` say so, and the entries below record why.

## Unreleased · the ffmpeg download moves on from an address whose bytes do not match the record

- **What was wrong.** The fallback below moved to the second address only when the first did not answer. An address that answered with bytes the SHA-256 record refuses (a changed file, a page where the archive should be, a truncated tarball) stopped the fetch with the first address's error, and the second address was never asked. FormDAM's fetch already tried the second address in that case; formcut now does the same.
- **The change.** `_download_first` became `_fetch_first(urls, path, report, cancelled, place)`: for each address it downloads, then calls `place`, which is `install()`, the check of every recorded file followed by placing them all. A failed download (httpx error, OSError) and a refused archive (`ValueError` from the check, `tarfile.TarError` for something that is not an archive) both go on to the next address; nothing is placed from an archive that failed, because `install()` places only after every file has matched. When no address works the `OSError` names each address with its own reason. A cancel still stops the loop, and an OSError while placing a good archive (a full disk) is not taken for a bad address. The override `FORMCUT_FFMPEG_RELEASE` is still the only address when set, so a wrong file there fails with no fallback. `setup/bundle_ffmpeg.py` does the same per address with a notice for each; when every address that answered had a build that does not match, it still fails the build (a differing build is never staged and never skipped silently), and its error names every address; when no address has the build at all it still stages nothing and leaves the fetch to first run. The addresses, the tag, the asset names, the per-person folder name and the record are unchanged.
- **Checked.** Four loopback servers on ports 27001 to 27007 outside the repo, before and after: first wrong and second right installed nothing before (ValueError, one request) and installs from the second after (two requests); both wrong installs nothing in both, now with an error naming both addresses and why each failed; first missing and second right installs from the second in both; the override set to a wrong file installs nothing and asks only the override in both. A first address answering with an HTML page, second right: ReadError before, installs from the second after. The same cases through `bundle_ffmpeg.main()` on 27011 to 27014.

## Unreleased · Connect Claude Code follows the app when it moves

- **What was wrong.** `POST /api/agents/install` for `claude-code` ran `claude mcp add formcut --scope user -- <command>` and took Claude Code's "already exists" as success without looking at what was saved. After the app moved (a new install folder, a copy run from Downloads), the button said "Already connected" while Claude Code still started the engine at the old path, which no longer exists.
- **The fix.** On "already exists" the route reads the saved entry with `claude mcp get formcut` and compares its `Command:` and `Args:` lines with this copy's `server_command()`. When they match it still answers `present: true`; when they differ, or the output cannot be read, it runs `claude mcp remove formcut --scope user` and adds the entry again, answering `present: false` (the window then says "Connected"). A re-add that fails is a 502 with Claude Code's message, as a first add was.
- **Checked.** With a stand-in `claude` on PATH that keeps its servers in a file, through the route on `app.main` (TestClient): before the fix, a connect from `/Users/me/Downloads/...` after one from `/Applications/...` answered `present: true` and the saved command stayed at `/Applications/...`; after it, the saved command is the new path, a second connect from the same place answers `present: true`, and the calls are add, get, remove, add. Not run against the real Claude Code CLI; the `get` output format is Claude Code's, and an unreadable one only costs a remove and add.

## Unreleased · the ffmpeg download tries formai-binaries, then formcut-binaries

- **Why.** The binaries repository is being renamed from `nodemode-dev/formcut-binaries` to `nodemode-dev/formai-binaries`. Until the rename the new address does not exist; after it, the old one redirects. Installed copies have the address compiled in, so both must work in either order of events.
- **The change.** `ffmpeg_fetch.RELEASES` holds both addresses, new first. `source()` returns the ordered list of archive addresses (only `FORMCUT_FFMPEG_RELEASE`'s when it is set, as before). `fetch()` goes through `_download_first`, which moves on from an address on an httpx error (a 404, a refused connection) or an OSError, re-raises a cancel, and raises one OSError naming every address when none answers. `setup/bundle_ffmpeg.py` loops over the same list with urllib, prints a notice per address that fails, and stages nothing when none answers. The archive from whichever address answered goes through `install()` unchanged: a file that differs from `ffmpeg-licence.json` installs nothing (the entry above moves on from such an address to the next). The tag `ffmpeg-<release>`, the asset name `ffmpeg-lgpl-<release>-<triple>.tar.gz`, the per-person folder, the env var names and the record are unchanged.
- **Checked.** Against a loopback HTTP server outside the repo with the two addresses pointed at it: new 404 and old serving installs from the old (two requests); new serving installs from the new (one request); neither serving raises naming both and installs nothing; old serving a changed ffmpeg is refused with nothing installed; new serving a changed archive was refused without trying the old (changed by the entry above); with `FORMCUT_FFMPEG_RELEASE` set to a 404 address only that address is asked. The same four cases through `bundle_ffmpeg.main()` behave the same. A refused connection on the first address moves on to the second; a cancel stops the loop.

## Unreleased · a seek near the end of an MPEG-TS file finds its frame

- **What was wrong.** With the stream origin added (the entry below), a seek target in the last seconds of an MPEG-TS file lay nearer its end, and the TS demuxer, which seeks by an estimate of the byte position, could land at the end of the file: the first decode after the seek gave nothing and the read reported the end of the stream. On a 20 s .ts starting at 1.48 s with a 2 s GOP, `frames.at` gave no frame at 18.0, 19.0 and 19.5 s. The reopen-from-start fallback also meant that a seek that overshot decoded the whole file up to the target, minutes a seek near the end of a long .MTS.
- **The fix.** `NativeSource._start` treats an empty first decode like a landing past the target: it seeks again 2, 4 and then 8 seconds earlier, decoding forward from wherever it lands, and reads the file from its start only if all of those fail. It counts the frames it decoded to reach the target (`seek_decoded`).
- **Checked.** A minute of MPEG-TS (offset 1.48 s, 2 s GOP) whose frames carry their own number in twelve one-bit blocks: seeks to 10, 30.04, 45.2, 57.9, 58, 59, 59.5 and 59.96 s land on ffmpeg's frame (`int(t * 25)`), and a seek ten frames before the end decodes at most ten seconds' worth of frames. On af6e4ee the 59, 59.5 and 59.96 s seeks found no frame. `frames.each(cfr=False)` is documented as not tone-mapping PQ, HLG or wide-gamut sources (the delivery check measures their signal).

## Unreleased · follow-up review: the worker pool at sixteen bits, stream origin and rotation, cadence and proxies

- **Ten-bit exports on the worker pool (critical).** With a ten-bit SDR export the encoder's pipe is opened for `rgba64le`, but `_render_span` built its renderers without `keep_sixteen`, so every pool worker wrote four-byte pixels into an eight-byte pipe: half the frames, scrambled, no error. Every ProRes export (always ten-bit) and every ten-bit SDR export without a GPU stack on three or more cores was hit (reproduced by the reviewer: 2 s at 25 fps gave 50 frames on one worker, 25 on three). The worker takes `keep_sixteen` from the main renderer, and both writers check each frame's byte count against the pipe's (width x height x 8 for a deep or sixteen-bit frame, else 4) and stop the export with that message when they differ. A ten-bit export keeps no resume cache: its sixteen-bit PNGs doubled the disk the export needs. Checked: ProRes at one and three workers (CPU path) both read back 25 frames, identical to the bit; with the old worker, the export now stops on the byte check instead of writing a scrambled file.
- **Stream origin.** `NativeSource._next` counted a frame's index from time zero. A file whose video starts later (MPEG-TS at 1.48 s, an offset mov) repeated its first frames and lost as many at its end; through `frames.py` that reached the cadence map, the delivery check, the source monitor and image-to-image. The index now counts from the stream's start (`start_time`, else the container's), a seek adds it back, and a seek that lands past its target (MPEG-TS seeks by byte position) reopens the file and decodes forward. Cadence maps written by this branch's earlier code exist only on machines that ran it: `frames.py` came in with 60c6d44 and was never released, so no shipped cache needs invalidating.
- **Rotation.** `NativeSource` swapped the width and height for a rotated stream but scaled the stored picture straight into them, so a phone's portrait video came out squashed. It scales at the stored size and turns the picture by the display matrix (`np.rot90`, the legacy `rotate` tag read with its opposite sign), as the pipe's ffmpeg does; a turned source skips formcut's own plane conversion.
- **Decoded frames.** `frames.each(cfr=False)` yields each decoded frame once, in presentation order. The delivery check uses it (it analyses the file as written); the cadence map keeps the timeline's clock, because `solve_clip` indexes it by time times the average rate, the frame the renderer shows. Callers close the reader with `contextlib.closing`.
- **Cadence.** The lookup of a running job, the submit and the record now happen under the engine's lock, taken before the job queue's own, which never calls back. The map is written to a temporary file and renamed into place, and one that does not load is measured again.
- **Auto-proxies.** Once records carried a codec, every HEVC and ProRes import queued a proxy. The codec rule now applies from 1080p up (the size rule already covers anything larger than 1080p, so a literal "above" would never fire); ProRes and DNxHD/HR are intra-only and fast to decode, so they earn a proxy by size alone. Builds run on two threads and at lower priority (`os.setpriority` 10 once started; `BELOW_NORMAL_PRIORITY_CLASS` on Windows).
- **Smaller.** A software encoder whose help lists no pixel formats (or could not be read) is not claimed ten-bit; the help is read from the binary the export runs. A `mov` export with no working `prores_ks` is refused (422 at the route, ValueError in `export_media`). A stored `activeTimeline` past the timelines, or not an int, reads back as 0.
- **Not done: APP_VERSION into app/version.py.** `--version` imports `app.main` to read it. The release tooling reads the version from `backend/app/main.py` (`setup/preflight.py`, `tests/test_family_versions.py`, and formcompiler's bump), so moving it is a change to the release process, left to the owner.
- **Checked.** `tests/test_followup_review.py`, 22 tests.

- **`formcut-engine --help`** (or `-h`) printed nothing and started the server; it prints the usage and exits 0, and `--version` prints the version.

## Unreleased · NTSC project rates as exact ratios

- **What was wrong.** A camera set to NTSC records at 24000/1001, 30000/1001, 60000/1001 or 120000/1001, and a project could not be made at any of them: `validate_document` refused a rate that is not a whole number ("Invalid project fps"), as did `projects.ProjectIn` (`fps: int`) when the window saved one, and a package import truncated it with `int()`. The same check broke the export rate presets: `export_media(..., rate="23.976")` on a 30 fps project rewrote the project's fps to 23.976 and the `FrameRenderer` refused it (59.94 the same; 29.97 from 30 is within the 0.2 % retime and kept 30).
- **The rule.** `app/rates.py`: a project rate is a whole number from 1 to 120 or one of the four NTSC ratios. `exact()` reads an int, a float or text ("30000/1001", "29.97") and returns a `Fraction`; a number within a hundredth of an NTSC rate means that ratio exactly, so 29.97 typed by a person and 29.97002997... carried by the window are the same rate. The document keeps the rate as a number (an int when whole, else the nearest float to the ratio), because the window's timecode, frame step and ruler maths take one; everything that names the rate to ffmpeg or a file takes it from `exact()`, so it is written as `30000/1001`, never a rounded float.
- **Where it applies.** `validate_document` (project and timeline rates), `automation` `project.settings` (so the RPC and the MCP tools refuse 240 at once rather than at render), `ProjectIn.fps` (`int | float`), package import, the export's output rate and the transparent export's `-r` (`rates.text`), and the export path choice: the native and layered graphs work on whole-rate timebases, so `fast_export.refusal` and `fast_layers.refusal` now say "a fractional frame rate" and such a project renders through the frame path, which samples frame k at k / rate. Before, only the native graph was held back; the layered graph would have taken `int(29.97)`. The rate presets gain 100, 119.88 and 120. Playback pacing, the proxy (pinned to the source's own `avg_frame_rate`) and the timeline files already worked on the exact grid: EDL, FCP 7 XML (timebase 30, ntsc TRUE), FCPXML (`frameDuration="1001/30000s"`) and OTIO (the rate as the nearest float, as OTIO keeps it).
- **Untrusted text.** A rate reaches `exact()` from documents, the API and agents. `Fraction(text)` would accept "1e999999999" or thousands of digits and build an enormous integer, stalling the engine (found in review). Text must now be digits, a ratio of up to six digits each, or a decimal of up to three digits and six places, at most 13 characters; ints are range-checked before any arithmetic, floats must be finite, a `Fraction` or a num/den pair is bounded, and the result must still snap to a whole rate from 1 to 120 or an NTSC ratio. 29 hostile inputs (exponents, 5000 digits, signs, zero, 0/0, x/0, inf, nan, over 120, huge ints and pairs) are refused in under 50 ms each.
- **Drop-frame.** Export writes non-drop timecode only (FCM: NON-DROP FRAME), labelled at the nearest whole rate, and the report says so; a drop-frame EDL from elsewhere is read on the drop-frame count. Writing drop-frame was not added.
- **MCP.** `formcut_create_project` and `formcut_set_frame` took `fps` as an int up to 240 while the engine stops at 120; they take a float from 1 to 120 and the description names the NTSC rates. `formcut_render`'s rate list names 100, 119.88 and 120. `setup/agents.py sync` regenerated the tool reference and its mirror.
- **Checked.** `tests/test_ntsc_rates.py`, 36 tests: `exact` on nine spellings and eight refusals; the document, a saved project and the RPC keep 30000/1001 and 60000/1001 and refuse 240; the MCP tools' bounds are 1 and 120; the stream at 29.97 and 59.94 stays on its grid; 29.97 (2 s), 59.94 (1 s) and 23.976 (1 s) projects export with `r_frame_rate` and `avg_frame_rate` of the exact ratio and 60, 60 and 24 frames; a 30 fps project exports at the 23.976 and 59.94 presets (red on 108107c: "Invalid project fps"); a 48-frame 23.976 clip on a 23.976 timeline renders and exports every frame in order; a proxy of a 29.97 source keeps 30000/1001 and 30 frames; the EDL of a 29.97 project comes back on the same frames, a drop-frame EDL is read on its count, FCP 7 XML and FCPXML carry the NTSC rate and come back on the same frames, and OTIO carries 24000/1001. The 10-bit 4:2:2 decode tests now also run at 29.97 and 59.94.

## Unreleased · proxy settings are kept and obeyed, and the agent tool's build flag builds

- **What was wrong.** `/api/proxies/settings` kept its two values in module globals (`renderer.PROXIES_ENABLED`, `proxies.DEFAULT_LONG_SIDE`), so both were lost when the engine restarted. A size set there reached no build that did not name one: `build_media_proxy` and `enqueue` took `DEFAULT_LONG_SIDE` as a default argument, which Python binds when the module loads, so Make proxy and every import still built at 1280. With proxies switched off, an import still queued a build. The POST took any JSON object and read `bool(body["enabled"])`, so `"false"` switched proxies on. And `formcut_media_proxy` sends `{"id", "build": true}` while `media.proxy` in `automation.py` read only `action`, so the tool answered "has been queued" and nothing was.

The POST body is a pydantic model with strict types and no extra fields; an unknown size is still 422. `media.proxy` takes `build: true` as `action: "build"` and refuses an unknown size as the HTTP route does. `renderer.PROXIES_ENABLED` is gone; nothing else read it.
- **Checked.** On 108107c, with `enqueue` recorded: size 960 set in settings, then Make proxy built at 1280; `{"enabled": "false"}` left proxies on; `media.proxy` with `build: true` queued nothing. `tests/test_proxy_controls.py`, 16 tests, covers each of those plus persistence across a reset of the cached settings, refusal of five bad bodies, a rebuild over a ready proxy, and imports with proxies on and off; all pass here. ## Unreleased · 10-bit 4:2:2 camera clips decode frame for frame

- **Why.** A reviewer is bringing mirrorless-camera footage: H.264 High 4:2:2 and HEVC Main 4:2:2 10, `yuv422p10le`, at 25 and 100 fps. The only 4:2:2 the suite made was ProRes, and `yuv.py` converts only 4:2:0 itself, so 4:2:2 goes through swscale to BGR in `VideoSource._as_bgr`. Nothing in the decode was changed; this adds the proof.
- **What the tests make.** `tests/test_r5_style_decode.py` encodes four one-second 384x216 clips at test time: H.264 intra-only (as an ALL-I recording) and HEVC with a 50-frame GOP (as IPB), each at 25 and 100 fps, tagged BT.709 limited range. A bright bar three pixels wide steps three pixels a frame, so the column it lands in names the frame; the chroma carries a pattern across and down. libx264 and libx265 are GPL and absent from the shipped LGPL ffmpeg, so a machine whose ffmpeg cannot write them skips with that reason, and one whose encoder refuses 10-bit 4:2:2 skips with ffmpeg's own message. The CI runners install Ubuntu's apt ffmpeg, Homebrew's and Chocolatey's, all GPL builds expected to carry both; that they write these streams was run here only for Homebrew's.
- **What they check.** ffprobe reads the codec, profile ("High 4:2:2 Intra" and "Rext", ffprobe's name for every HEVC range extensions profile), pixel format, rate and frame count back; the engine's probe reads size, rate, duration and pixel format with ffprobe and, as the LGPL bundle runs, with ffmpeg alone; reading from frame 0 through both decoders (PyAV in the engine and the ffmpeg pipe, hardware decode off) gives exactly 25 or 100 frames, each the bar's own frame in order, with the first and last within a mean of 3 levels of ffmpeg's own BGR decode; seeking straight to the last frame gives frame 24 or 99; and a 100 fps project renders source frame n at n / 100 for all 100 frames. 30 tests; all pass here with Homebrew ffmpeg 9.0.2, and all 30 skip with libx264 and libx265 hidden from it.

## unreleased (after 2.15.8) · ten- and twelve-bit sources keep their steps through decode, grade and LUT

- **What was wrong.** A review of another editor found shadow banding grading Canon R5 C Canon Log 3 10-bit 4:2:2 footage, and formcut had the same weakness. On an SDR timeline every source reached the renderer as bytes: `NativeSource._as_bgr` asked swscale for `bgr24`, formcut's own converter (`yuv.py`) made bytes even of a `yuv420p10le` frame, and only a PQ or HLG source on an HDR timeline came through at sixteen bits. The grade (`color_grade.apply`) and the LUT (`assets.apply_lut`) then worked on those bytes and wrote bytes, and a strong shadow lift stretched 32 byte levels of shadow over about a hundred output levels, five or six apart. The layered export graph decodes to `bgr24` before its baked cube, so it banded the same way. There were no camera Log input transforms, and 1D .cube files were refused.
- **Decode.** `VideoSource` reads the stream's bit depth (`bit_depth`, from the pixel format) and, when the renderer asks for `precise` (an SDR timeline with the sixteen-bit canvas, `FrameRenderer.precise`), a source of more than eight bits is `wide`: RGBA64 from swscale for 4:2:2 and 4:4:4, formcut's own planes at sixteen bits for 4:2:0 (now 12-bit 4:2:0 too), and the colour pipe's zscale or colorspace step ends at `yuv444p16le` or `yuv444p12` instead of `yuv420p`. An 8-bit source is unchanged, decoders are pooled per `(path, limit, deep, precise)`, and the helpers that read media for a model (brush, matte) ask for bytes. An HDR timeline is unchanged: there, a 10-bit SDR source still decodes as bytes and is lifted (left for the owner).
- **Grade, panel, LUT.** Each works in float32 on a sixteen-bit picture and rounds once to sixteen bits: the colour panel's NumPy reference (the Rust kernel stays the byte path); a separable grade (wheels, contrast, master and channel curves) as one 65536-entry curve a channel evaluated by `apply_float`, anything else as the 33-point lattice sampled trilinearly in float32 with exact weights (`cv2.remap`, which the byte path uses, puts its weights in 32nds of a cell: ten-bit positions); a 3D LUT trilinearly or tetrahedrally (`lutInterpolation`, trilinear by default), a 1D LUT per channel at every input level. `sample_3d` runs a large picture in bands on a thread pool, since NumPy's gathers release the interpreter lock. The byte path of every one of them is the code it was: a frame from an 8-bit source is the same frame, to the bit, as with `FORMCUT_PRECISE=0`, on the CPU and on the device (`test_the_eight_bit_fast_path_is_the_frame_it_was`). Between steps the picture is carried at sixteen bits, so "float end to end" is float inside each step and a 1/65535 rounding between them, 64 times finer than a ten-bit step.
- **Quantised once, dithered.** The frame is rounded to bytes once at the end, as the sixteen-bit canvas already was, but a frame that carried a sixteen-bit layer is rounded with an 8 x 8 ordered dither in integers, `floor(v / 257 + (2k + 1) / 128)`. A value that is already a byte stays that byte, so a frame with nothing finer than bytes comes out as before; ordered rather than random so preview and export, CPU and device, and golden frames are deterministic. When the device composites, such a frame is read back at sixteen bits (pack16) and dithered here, so both paths dither with one function. An adjustment clip over such a frame grades the sixteen-bit canvas instead of bytes.
- **The device.** `QUANTISE_CODE` and the LUT passes round to the layer's own grid (65535 for a sixteen-bit layer, 255 for bytes, as before); the LUT pass gained tetrahedral sampling and `LUT1D_CODE` is the 1D pass; `effects_and_warp` and `apply_effects` give a sixteen-bit picture back at sixteen bits. An HDR timeline's sixteen-bit layers also now round to 65535 after device effects, where they rounded to bytes, which the CPU never did.
- **Camera Log (`camera_log.py`).** `inputColour` is `canon-log3`, `canon-log2` (Cinema Gamut), `slog3` (S-Gamut3.Cine), `vlog` (V-Gamut) or `logc3` (ALEXA Wide Gamut, EI 800). The decoded signal is read as the camera's code value / 1023 (all four makers define their curves on full-range code values; a video-range file decoded as video range is mapped back through 64 and 876), turned to scene light by the maker's curve, moved to Rec.709 primaries by the matrix computed from both sets of primaries and D65, given a shoulder above 0.75 (`KNEE`, unchanged below, `knee + (1 - knee) t / (1 + t)` above) and encoded with the BT.709 OETF, so grey lands at 41 percent and 90 percent white at 92, as a camera's own Rec.709 mode puts them. The output is sixteen bits (bytes on an HDR timeline, which lifts bytes; a Log to HDR transform is left for the owner). It runs on the CPU before the colour panel and the grade, so a clip with one is never sent to the device as planes; the device path then takes the result like any graded layer. `media._probe` records `bitDepth` and, when the file's tags or a camera's metadata near its start or end name a Log (`camera_log.suggest`, Sony's `CaptureGammaEquation` item among them), `inputColourSuggestion`; the interface offers it and applies nothing by itself. Both fast export paths refuse `inputColour`, and the layered graph refuses a graded source of more than eight bits.

Canon USA, "Canon Log Gamma Curves: Description of the Canon Log, Canon Log 2 and Canon Log 3 Gamma Curves", white paper, 2018-11-01 (the full-range forms of Canon Log 3 and the revised Canon Log 2, reflectance = scene linear x 0.9, and the code values 128, 351, 577 and 908 for Canon Log 3, 95, 407, 575 and 797 for Canon Log 2). ## 2.15.6 · volume keyframes reach the mix and the export

- **What was wrong.** Volume is written two ways: `volumeKeys` (`{t, value}` points, K4) and `keyframes[].props.volume`, the shape `rhythm.ducking` returns and the inspector's Duck button writes onto the music clip. `timing.volume_at` read only `volumeKeys` and the static `volume`, so a duck never reached `audio_render.clip_envelope`. `validation.clip_values` also refused `volume` as an animated property, so a document carrying the duck failed `validate_document` ("Unknown animated property") before any mix was made.
- **The fix.** `volume_at` is `volumeKeys` (or the static volume) times `property_at(clip, "volume", t, 1.0)`. The keyframes are a gain on top of the clip's level, the way the ducking helper means them (1.0 is "as set", `depth` is what the music drops to), so a music clip at 0.9 stays at 0.9 between ducks rather than jumping to 1.0. With both written the two multiply; with no volume keyframes the factor is exactly 1.0, so clips with `volumeKeys` or no keys are unchanged. The points ease as transform keyframes do (`interp`, `handles`, held before the first and after the last). `clip_envelope` still clamps the product to 0 to 4. Validation takes `volume` keyframes in 0 to 4, the same range as `volume` and `volumeKeys`.
- **Preview and export.** Playback in the window is the engine's own mix (`AudioPlayback` renders `/api/render/audio`, which is `render_audio`), so fixing `volume_at` fixes what is heard and what is exported in one place. The native and layered export paths take the frame path's wav from `render_audio` before choosing a path, and `fast_export._plain` refuses only picture keyframes (`MOTION`), so a clip with sound keyframes alone stays on the native path and is ducked there too. `LiveMixer.fadeGain` still plays the static volume only; it is reachable from `window.formcut.liveMix` but nothing in the window plays through it.
- **Checked.** `tests/test_volume_keyframes.py`, 10 tests: `volume_at` on a 1.0 to 0.2 to 1.0 duck, the product with `volume` and with `volumeKeys`, picture keyframes leaving volume alone, `mix_audio` on a 440 Hz tone (RMS at 1.3 to 1.7 s over 0.2 to 0.8 s is 0.2), the same duck through `export_media` on the native and the frame path (0.2 inside, 1.0 after it, decoded back from the file), and validation bounds. With `timing.py` from 2.15.5, 6 of the 10 fail; with this change all pass.

## 2.15.5 · EDL timecodes count frames on the grid the window shows

- **What was wrong.** `interchange._timecode` counted `round(seconds * round(fps))`, the rounded rate, while the window's `formatTimecode` (2.15.5) counts `floor(seconds * fps + 1e-6)`, the exact rate. ## 2.15.5 · object removal ingests only a complete clip and never leaves a partial one

- **What was wrong.** In `planar_api.remove_object`, a cancel broke the frame loop and a closed pipe was swallowed, and when ffmpeg then exited 0 the short clip was ingested into the media bin and the job reported every frame. Any other exception in the loop (a fill or a frame read failing) closed ffmpeg's input, ffmpeg finalised what it had, and the partial `.mkv` stayed in `renders/`.

## 2.14.0 · extension host (Form Extension Contract, API 1)

- **Kit vendored unchanged.** `app/formext_host.py` is the contract kit's resolver and file checks, byte for byte, so every Form app refuses the same manifests with the same words. It is excluded from ruff in `ruff.toml` because formatting it would make it differ from the kit; `app/extensions.py` wraps it.
- **Routes from the features tuple.** `app/extensions.py` is one more entry in `features.py`, as the invariant says. The list is cached against `kit.stamp` (the two files' modification times), so the 2 s poll from the window costs two `stat` calls; `?reload=true` re-resolves regardless, which is how a development extension's edited manifest is picked up without touching `dev.json`.
- **Origin exemption, narrow.** `LocalOnly` refuses any request whose Origin is not the window's and any cross-site request with no Origin. A sandboxed frame has an opaque origin, so its module scripts arrive with `Origin: null` and its stylesheet and image loads with no Origin and `Sec-Fetch-Site: cross-site`. `GET` and `HEAD` under `/api/extensions/files/` from loopback are let through with any Origin and any `Sec-Fetch-Site`, as the contract's 07:47 wording says (the integration pass widened the first cut, which allowed only absent or `null` Origins and GET, and added HEAD to the route, which had answered it with the SPA's 404). The prefix serves only a package's own files and changes nothing; every other route still refuses `Origin: null` and web origins (403). The files are the package's own, served with `Access-Control-Allow-Origin: *` as the contract asks.
- **404 with headers.** A refused file answers 404 with no body but still carries nosniff, no-store, CORP and ACAO. `LocalOnly` adds its own nosniff too, so that header appears twice; harmless, left rather than special-casing the middleware.
- **Dialogs and save stay in one request.** `/api/extensions/save` opens the system save dialog and writes in the same request, so the path always comes from the person's own choice; there is no "write bytes to this path" route an extension page could reach. `/api/extensions/open` reads only what the dialog returned, filtered by `accept`, 200 MB in total.
- **Fetch only to the public internet.** formcut already reaches the network (stock, registry, cloud), so `net.fetch` is offered, through the engine because the frame's CSP has `connect-src 'none'`. https only, no redirects followed (the extension sees the 3xx and decides), cookies and formcut's own headers stripped, and every resolved address must be global: loopback, private, link-local and multicast are refused. A DNS answer could still change between the check and the connect; accepted for a permission the person granted by name.
- **The window bridge.** There was no route from the MCP server to the window, and extension pages, their consent and their storage live in the window. `ask_window` queues a request; the window long-polls `GET /api/extensions/agent/next` (25 s) and posts the answer to `/api/extensions/agent/{id}`. A request nobody claims in 15 s means no window is open, and says so (6 s was too short on a loaded machine, where the window's next poll took longer to arrive). `extensions.list` then falls back to the engine's own view without permission state.
- **RPC in the thread pool for these two.** `http_rpc` is async and calls the synchronous dispatcher on the loop thread. `extensions.command` waits for the window, and the window answers through the same loop, so waiting there deadlocked until the timeout. Only methods starting `extensions.` are moved to `run_in_threadpool`; every other method keeps running as before. The `/api/rpc/ws` websocket does the same (integration pass: it ran them on the loop and would have stalled the whole engine for up to 150 s). `app.cli`'s framings run in their own process, where no window ever polls.
- **Fail at once with no window.** The contract asks a CLI that cannot reach a window to fail at once. `agent_next` records when a window last polled; `ask_window` refuses straight away when none has in 35 s (one 25 s long-poll plus slack), so `app.cli` and an engine with its window closed answer "the formcut window is not open" immediately instead of after the 15 s claim wait.
- **Prefixed tool names.** The MCP tools are `formcut_extensions_list` and `formcut_extension_command`: every formcut tool carries the `formcut_` prefix, and the contract (07:47 resolution) names them `<prefix>_extensions_list` and `<prefix>_extension_command` on such servers. The README count is 34. `_rpc` gained a `timeout` argument so the command tool can wait 180 s (the window allows 150 s for a command plus the consent dialog).
- **Save without a dialog.** `/api/extensions/save` with `downloads: true` writes into `~/Downloads` (created when missing) as `name (2).ext` when the name is taken, the contract's fallback for a host with no save dialog. Only the base name is used, leading dots stripped, so the window's confirm dialog cannot aim it elsewhere. The window sends it only after the person confirms the name in formcut's own dialog.
